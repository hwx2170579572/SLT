# Scene-representation redesign: environment evidence

Date: 2026-10-03. This note records read-only source and existing-result evidence for a new scene representation on `intersection_sorted_depart4p0`, with SAC and critic input interface `z_t, a_t` retained. No training, simulation, evaluation, or tests were run; no code was changed. The key implementation distinction is that names such as “route” describe path geometry in the observation; they do not necessarily mean the policy receives an actor's assigned future SUMO route.

## Scene and task geometry

`intersection_sorted` uses the fixed SUMO network `envs/sumo/original_scenarios_v1/intersection_sorted/map.net.xml`. It has one central junction `J1`, four approaches, three 70 m lanes per approach, and an unregulated junction. The network lists multiple internal via lanes for turn/through movements and a junction foe/conflict request matrix; there is no traffic-light program in this network file. The ego task is fixed: `ego.rou.xml` specifies route `-E1 -E0`, departure on `-E1_2`, and arrival on `-E0_1`. The only `-E1` to `-E0` movement is lane 2 to lane 1 through internal lanes `:J1_14_0` and `:J1_21_0`. Thus route-compatible approach-lane choice is a real task constraint, not an inferred collision label. See [paper_scenario_registry.py](../../envs/sumo/paper_scenario_registry.py#L74-L103), [ego.rou.xml](../../envs/sumo/original_scenarios_v1/intersection_sorted/ego.rou.xml#L3-L5), and [map.net.xml](../../envs/sumo/original_scenarios_v1/intersection_sorted/map.net.xml#L94-L136) [#L165-L202].

The static map can support more than one conflict relation inside this one `J1`; it is not a network of several intersections. For example, the ego left-turn via path converges on `-E0_1`, which is also the destination of the `-E3_1 -> -E0_1` straight movement. The XML exposes the movement connections, via lanes, geometries, and foe indices, so a future representation can define multiple movement-pair conflict regions or merge/exit occupancy regions from static geometry. The repository's topology builder already creates successor/predecessor, left/right, conflict, and merge relations from the static network. It does not provide named conflict-zone IDs or a policy-level zone occupancy timeline today. A zone partition would therefore be a new, explicitly defined derived representation; “multiple connectors” alone should not be reported as a count of separate junctions or proof of a specific impact location. See [map.net.xml junction](../../envs/sumo/original_scenarios_v1/intersection_sorted/map.net.xml#L136-L163), [movement connections](../../envs/sumo/original_scenarios_v1/intersection_sorted/map.net.xml#L165-L207), [topology_graph.py successor relations](../../envs/sumo/topology_graph.py#L171-L216), [conflict construction](../../envs/sumo/topology_graph.py#L255-L340), and [topology_graph_v2.py](../../envs/sumo/topology_graph_v2.py#L310-L377).

The 30 fixed traffic templates contain only three distinct route edge sequences: `E2 E1`, `-E3 -E0`, and `E0 E3`. These are straight-through movements from three directions; the template pool does not establish left/right-turn intent uncertainty. The D1 `depart_scale=4.0` path multiplies each source vehicle's departure time by four and keeps the route assignment, rather than synthesizing new movements. The background still has heterogeneous driving parameters (`speedFactor`, `minGap`, impatience/cooperation, `sigma`, and `jmIgnoreFoeProb` in the route files), so fixed route does not imply fixed arrival time, yielding behavior, or conflict occupancy. It does mean that a learned distribution over arbitrary background route intentions is not an evidenced primary need in this benchmark. Generalization to traffic with turns or route alternatives would need a separate held-out scenario/template evaluation. See the 30 files under [intersection_sorted/traffic](../../envs/sumo/original_scenarios_v1/intersection_sorted/traffic), [train_intersection_yield_v2.py](../train_intersection_yield_v2.py#L119-L150), and [paper_scenario_registry.py](../../envs/sumo/paper_scenario_registry.py#L94-L103).

An exit queue is geometrically possible: the ego's left movement joins `-E0_1`, a lane also reached by background straight traffic from `-E3_1`. Existing final-evaluation evidence does not establish that a downstream queue caused the observed failures. The repaired ST-RT collision episodes ended with the last available ego lane on `:J1_21_0` or `:J1_14_0`, and their terminal planned-route continuation was reachable; that identifies connector-region last observations, not the impact point, collision partner, or whether an exit queue caused contact. The repaired ST timeouts include both route-incompatible history and `route_has_no_next_edge`; all five had prolonged stopping, but the last reason is not automatically a wrong-lane label. Keep “entry timing / conflict occupancy / exit clearance” as testable task questions, not conclusions. See [failure position and route summary](../st_strt_four_way_failure_audit_20261003.md#L33-L50) and [timeout table](../st_strt_four_way_failure_audit_20261003.md#L69-L80).

## What the present policy observation contains

For the active D1 environment, `SumoSceneEnv` defaults to 10 history samples, ego plus five neighbors, five trajectory fields, and 10 path points. `PaperScenarioSpec` sets two candidate map paths per actor and five map channels, with one-metre waypoint spacing for this paper scene. The resulting base arrays are therefore `trajectory [6,10,5]` and `map [12,10,5]`. Each sample is gathered at a 0.1 s SUMO raw tick; `action_repeat=3` gives a nominal 0.3 s policy interval, so the stored ten-frame history spans about one second. It is not a dense, long-horizon track. See [sumo_env.py](../../envs/sumo/sumo_env.py#L244-L328) [#L1769-L1801], [paper_scenario_registry.py](../../envs/sumo/paper_scenario_registry.py#L20-L40), and [train_intersection_yield_v2.py](../train_intersection_yield_v2.py#L75-L95).

The trajectory state is read from TraCI as center position `(x,y)`, heading, and two speed-derived channels. SUMO's returned vehicle position is front-bumper based, so the environment shifts it to the center using vehicle length. For the inherited SMARTS contract, heading is north-zero and the legacy channels are `speed*cos(heading), speed*sin(heading)`; those are retained for source compatibility and should not be mistaken for a Cartesian velocity vector. Acceleration is not directly queried or included. A redesigned representation can compute consistent Cartesian velocity from the simulator's scalar speed and orientation, and optionally estimate acceleration from timestamped history, but must define wrap, missing-frame, and differencing semantics. The geometry/OBB collision code uses provider-class dimensions, while dimensions are not policy features; the scene uses `include_pedestrians=False`. See [sumo_env.py](../../envs/sumo/sumo_env.py#L38-L51) [#L90-L104] [#L1705-L1754] [#L1610-L1648], and [paper_scenario_registry.py](../../envs/sumo/paper_scenario_registry.py#L20-L33).

Current actor selection does not model a sensor radius or occlusion. `PaperSumoSceneEnv` sets `neighbor_radius=inf`; the base environment considers all currently active vehicles, sorts by distance then actor ID, and places only the nearest five into the policy tensor. Ego is slot zero. The tie-break ID is not itself an observation feature. IDs are used internally to maintain per-actor caches, and diagnostics can recover actor keys, but the policy receives neither IDs nor the full active-vehicle set. Social actors first seen late have padding; if a tracked actor disappears for raw ticks and reappears, the SMARTS adapter interpolates missing samples. The standard trajectory array has no explicit actor-valid or per-frame-valid mask: zero padding is decoded through a legacy nonzero-coordinate proxy. The optional `state_lstm_mask` only covers that separate optional key and is disabled in this D1 environment. An explicit presence/age mask and stable track association are therefore meaningful input-contract changes. See [paper_env.py](../../envs/sumo/paper_env.py#L111-L117), [sumo_env.py](../../envs/sumo/sumo_env.py#L1757-L1767) [#L1803-L1832] [#L1866-L2019], and [features.py](../../algos/sb3_torch/features.py#L44-L50) [#L442-L463).

Policy observations contain no explicit road ID, lane ID, route index, next edge, route-reachability label, signal state, or right-of-way/priority feature. Those values are obtainable inside the SUMO process through TraCI and are written by optional behavior diagnostics, but they are not ordinary policy inputs. The fixed ego task route itself is public in the static task file; the current base policy tensor does not encode it as an explicit goal/target edge. A new task-goal signal may use the published ego mission, but any TraCI-derived current-lane/reachability annotation should be declared and supplied consistently to all re-trained comparisons. Do not silently feed evaluation-only route diagnostics or hidden future actor intent to the policy. See [sumo_env.py](../../envs/sumo/sumo_env.py#L731-L809) [#L960-L1005] [#L1966-L2022], and [ego.rou.xml](../../envs/sumo/original_scenarios_v1/intersection_sorted/ego.rou.xml#L4-L5).

## Path geometry is not hidden social future route

The environment constructs a `map` block for each selected actor. `_actor_paths` queries TraCI route fields, but under the active SMARTS observation contract those fields do not become a neighbor's assigned future route: `_smarts_waypoint_polylines` ignores `route` for social actors on a normal edge and enumerates lane-graph continuations with `allowed_edges=None`; inside a junction it uses only the current internal edge and its outgoing lanes. The actual D1 factory uses `YieldObsIndependentV2EnvV1`, whose ego branch also enumerates the public lane graph with `allowed_edges=None` and puts the current ego lane first. This preserves the left-turn curve through internal lanes, but the candidate geometry is not a direct label of the ego's fixed mission. Both ST and ST-RT environments construct these maps. D1 config enables `use_route=False` for ST and `use_route=True` for ST-RT; “RT” therefore means the learned encoder reads candidate path geometry, not that it gets every vehicle's hidden future route or a route-prediction label. See [sumo_env.py](../../envs/sumo/sumo_env.py#L1966-L2108) [#L2211-L2290] [#L2341-L2378], [yield_obs_env.py](../yield_obs_env.py#L34-L91), [train_intersection_yield_v2.py](../train_intersection_yield_v2.py#L230-L258), and [train_intersection_yield_v2_d1.py](../train_intersection_yield_v2_d1.py#L727-L730).

The separate ConflictTiming/Longres observation path is also bounded and public-geometry based. Its wrapper reads the current trajectory row, the currently observed actor keys, and their current road/lane IDs; it enumerates the ego's candidates subject to the known ego task route and social candidates with `route=None` from static legal lane successors. Defaults are at most eight ego and four social paths, 60 m look-ahead, and a 10 s constant-current-speed timing horizon; the kernel supports nonparallel crossing-corridor relations only. It explicitly records `social_future_routes_read=false`. This current-lane TraCI lookup is an extra input-building privilege compared with a pure array-only map-matcher, but it is not hidden future-route access. Longres reuses this bounded conflict-timing input and changes the policy with a bounded longitudinal residual; it does not make timing a causal forecast of arbitrary future actions. If a redesigned representation reuses this signal, it should retain the candidate limits, unknown/unsupported cases, and provenance or compare all methods under the same disclosed current-lane information. See [conflict_timing_observation.py](../../envs/sumo/conflict_timing_observation.py#L201-L314) [#L381-L550] [#L605-L674], [route_conflict_timing.py](../../envs/sumo/route_conflict_timing.py#L145-L166), and [train_intersection_yield_v2_d1.py](../train_intersection_yield_v2_d1.py#L740-L760).

The optional static lane topology is richer than current ST/ST-RT input: it can include sampled lane geometry, lane width/speed/curvature/internal/lane-index attributes and typed successor, predecessor, left, right, conflict, and merge edges. Its padded capacity is not the current valid graph size, and D1 ST/ST-RT config has `use_topology=False`. A representation using movement and conflict-region nodes is feasible from public static lane shapes/connections/foe metadata, but dynamic occupancy must be computed from the policy-visible vehicle states and explicit masks. It must not turn topology-builder conflicts into proof that an observed episode ended in that exact conflict region. See [topology_graph_v2.py](../../envs/sumo/topology_graph_v2.py#L286-L405) and [train_intersection_yield_v2_d1.py](../train_intersection_yield_v2_d1.py#L727-L730).

## Implications for a fair full input redesign

- Keep the SAC actor/critic interface `z_t,a_t` fixed while replacing the observation encoder, but define a single observation contract for all newly trained baselines and variants. That contract should specify the same actor candidate set/radius, task goal, map/topology, masks, history sampling, coordinate frame, and any current-lane map-matching for every method. Preserve seed, traffic templates and departure scaling, raw-step budget, final checkpoint rule, and validation seeds. The historical single-seed results remain descriptive comparisons because they did not all use a newly unified observation contract.
- Model the observed scene as current measured actors plus static/legal movement possibilities. Use the fixed task route for the ego as public task conditioning; represent social-agent intent as a set of legal continuations or an explicit unknown/alternatives field, not an assigned future SUMO route. Keep physical velocity Cartesian and heading convention documented; expose actor/frame validity, observation age, and timestamp instead of inferring them from `x != 0` or zero-filled slots.
- A movement/conflict occupancy graph is supported by this network's internal geometry and foe matrix, and an explicit shared-exit/merge node is defensible from the `-E0_1` connections. But the present evidence demonstrates connector-local terminal observations and five ST stagnation timeouts, not that all STRT collisions are a particular side-impact type, that traffic queues caused them, or that multiple zone clearing is the observed causal bottleneck. Treat that representation as a testable encoding hypothesis; check whether it improves entry/clearance and collision outcomes with the same input information across methods.
- The 30 traffic templates' straight-only movement structure makes this a useful fixed-route crossing task but a weak test of route-intent uncertainty. Any claim about multimodal intention representation needs a separate held-out scene/template with real route alternatives or turning flows; do not infer that contribution from this benchmark alone.

The previously discussed policy-consistent event-value/critic route remains a backup option at the user's request; it is not part of this observation audit and has not been promoted as the current priority.
